## Phase 2: Medium Effort

### F-21: Unbounded Map growth in `error-lifecycle.ts`

**Severity:** MEDIUM | **Effort:** Medium
**File:** `src/store/error-lifecycle.ts`

The `states` Map grows with every unique fingerprint and is never pruned. In a long-running session with many distinct errors, this leaks memory. The ring buffer evicts old events, but the lifecycle tracker retains their resolution state forever.

**Fix:** Add a `MAX_LIFECYCLE_ENTRIES` cap (e.g., 1000) with LRU eviction, or periodically prune entries older than a threshold (e.g., 10 minutes since `lastSeen`). The audit buffer's shift-on-overflow pattern is a good model.

---

### F-22: Unbounded endpoint Map growth in `perf-baseline.ts`

**Severity:** MEDIUM | **Effort:** Medium
**File:** `src/store/perf-baseline.ts`

Each unique endpoint path creates a new Map entry. Per-endpoint samples are bounded (`MAX_SAMPLES_PER_ENDPOINT = 100`), but the number of unique paths is not. Apps with dynamic path segments (e.g., `/api/users/:id`) could create thousands of entries.

**Fix:** Add a `MAX_TRACKED_ENDPOINTS` cap (e.g., 200). When exceeded, evict the endpoint with the fewest samples. Alternatively, normalize paths before recording (strip numeric segments: `/api/users/123` → `/api/users/:id`).

### F-23: `verify-build.ts` lacks error handling around `JSON.parse` of sub-tool results

**Severity:** HIGH | **Effort:** Medium
**File:** `src/tools/verify-build.ts` lines 45, 60

```typescript
const tscData = JSON.parse((tscResult.content[0] as { text: string }).text);
```

If `handleRunAndWatch` returns an error result (e.g., command not found, security rejection), the response text won't be valid JSON for the expected schema. `JSON.parse` will throw, or the subsequent property access (`tscData.success`, `tscData.error_count`) will fail with a TypeError. No try/catch wraps these calls.

**Fix:** Wrap each step in try/catch, or validate the sub-tool result before parsing:
```typescript
const tscText = (tscResult.content[0] as { text: string }).text;
let tscData: Record<string, unknown>;
try {
  tscData = JSON.parse(tscText);
} catch {
  steps.push({ step: "typecheck", pass: false, detail: "Failed to parse typecheck output" });
  return result("FAIL", steps, [{ raw: tscText }]);
}
```

### F-24: Command injection risk in `error-narratives.ts` suggestions

**Severity:** MEDIUM | **Effort:** Medium
**File:** `src/scoring/error-narratives.ts` lines 41, 52, 113

Regex-captured values from error messages are interpolated directly into command strings:

```typescript
command: `pip install ${m[1]}`,        // m[1] from error message
command: `npm install ${m[1]}`,        // m[1] from error message
command: `lsof -i :${m[1] || m[2]}`,  // m[1]/m[2] from error message
```

Error messages come from user application logs, which could contain crafted content. If an agent executes these commands verbatim, a malicious log line like `Cannot find module 'foo; rm -rf /'` would produce `npm install foo; rm -rf /`.

The risk is mitigated because:
1. The regex captures `\S+` (no spaces), limiting what can be injected
2. The agent should validate commands before execution
3. `run_and_watch` has an allowlist

But the `lsof` command uses `|` (pipe) which could be exploited.

**Fix:** Sanitize captured values before interpolation. At minimum, strip shell metacharacters (`; | & $ \` ( ) { } < >`):
```typescript
function sanitizeForCommand(value: string): string {
  return value.replace(/[;&|$`(){}<>]/g, "");
}
```

### F-25: Response-wrapping boilerplate still not extracted

**Severity:** MEDIUM | **Effort:** Medium
**Carries forward:** MRR-001 F-07

`jsonResult`/`errorResult` helpers remain private to `server.ts`. New tool handlers (`get-migration-status.ts` has 4 instances, `get-perf-baseline.ts` has 2, `get-error-clusters.ts` has 1) continue to inline the `{ content: [{ type: "text", text: JSON.stringify(...) }] }` pattern.

`verify-build.ts` extracted its own local `result()` helper (line 89), which is a step in the right direction but creates a third variant of the same pattern.

**Fix:** Extract `jsonResult` and `errorResult` to `src/mcp/response-helpers.ts` and import across all tool handlers. The `verify-build.ts` local `result()` can delegate to `jsonResult`.

## Positive Observations

1. **New parser quality** — The 6 new parsers (pydantic, celery, sidekiq, bullmq, cargo-test, junit) follow the established `ErrorParser` interface exactly. Each has clear regex patterns, proper JSDoc, and consistent `scoring_hints` usage.

2. **Store module design** — `audit-buffer.ts` and `perf-baseline.ts` use clean factory functions returning interface objects. The audit buffer has proper bounded growth. Both are well-documented.

3. **Error lifecycle concept** — The `filterActive` approach (post-query filter, not buffer mutation) is architecturally sound. It keeps the ring buffer as the single source of truth while adding resolution semantics on top.

4. **Composite tool pattern** — `verify-build.ts` demonstrates good tool composition (calling `handleRunAndWatch` internally). The early-exit-on-failure pattern is clean.

5. **Error narratives** — The pattern-matching approach with ordered specificity is well-designed. Covering 10 common error patterns with actionable fix suggestions adds real value.

6. **Rules directory** — The Cursor, Claude Code, and Kiro integration files are well-written, agent-appropriate, and consistent with each other. They correctly prioritize TracePulse tools over terminal output.

7. **Frontend crash bridge** — Clean separation between validation (`validateCrashReport`), conversion (`crashReportToEvent`), and the user-facing snippet (`error-boundary-snippet.ts`). Input truncation is applied at the validation boundary.
