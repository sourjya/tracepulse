## Executive Summary

TracePulse has strong test coverage for its core pipeline, parsers, and store layers. However, **21 of 91 non-trivial source files have no dedicated test file** (77% file-level coverage). The most critical gaps are in the `src/tools/` directory (13 of 27 tool handlers untested) and `src/infra/` (3 of 5 modules untested). A `makeEvent()` factory function is copy-pasted across **23 test files** — the single largest maintainability debt in the test suite. Several collector tests use real `setTimeout` delays (2.5s each), making them slow and flaky.

**Finding Summary:**
- HIGH severity: 7 findings
- MEDIUM severity: 9 findings
- LOW severity: 4 findings

## 2. Findings

### HIGH Severity

#### H1: `makeEvent()` factory duplicated across 23 test files

**Files:** 23 test files (see Section 1 grep results)
**Impact:** ~460 lines of duplicated boilerplate. When `RuntimeEvent` gains a new required field, all 23 copies must be updated in lockstep — a guaranteed source of future test breakage.

**Recommended fix:** Extract a shared `tests/helpers/make-event.ts` module:
```typescript
// tests/helpers/make-event.ts
export function makeEvent(overrides: Partial<RuntimeEvent> = {}): RuntimeEvent { ... }
export function makeFrontendError(overrides: Partial<FrontendError> = {}): FrontendError { ... }
```
Import from all test files. Also extract `makeFE()` / `makeBE()` (duplicated in 2 files).

#### H2: 8 tool handlers have zero test coverage

**Files (untested):**
- `src/tools/check-port.ts`
- `src/tools/restart-server.ts`
- `src/tools/register-probe.ts` (6.5KB — largest untested file)
- `src/tools/get-project-health.ts`

- `src/tools/empty-diagnostics.ts`
- `src/tools/correlate-with-diff.ts`
- `src/tools/get-requests.ts`

**Impact:** These are MCP-facing tool handlers — the public API surface. Regressions here are invisible until an agent calls the tool and gets a broken response.

**Recommended fix:** Create `tests/unit/tools/<tool-name>.test.ts` for each. Priority order: `register-probe` (largest, most complex), `correlate-with-diff` (git interaction), `check-port` (network), then the rest.

#### H4: Collector tests use real `setTimeout` delays — slow and flaky

**File:** `tests/unit/collectors/multi-process-collector.test.ts`
**Evidence:** 7 occurrences of `await new Promise((r) => setTimeout(r, 2500))` — each test waits 2.5 seconds for a process to finish.

**File:** `tests/unit/collectors/process-spawner.test.ts`
**Evidence:** Multiple `await new Promise((r) => setTimeout(r, 300))` calls.

**Impact:** These tests take ~12.5s combined (visible in test output: individual tests at 2500ms+). They are timing-dependent — on a slow CI machine, 2.5s may not be enough; on a fast machine, it's wasted time.

**Recommended fix:** Replace fixed delays with event-driven waiting. The collector emits events when processes exit — wait for those events instead of sleeping. Alternatively, use `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()` as done correctly in `watch-controller.test.ts` and `score-decay.test.ts`.

#### H7: `http-transport.test.ts` is a stub — only 4 trivial assertions

**File:** `tests/unit/transport/http-transport.test.ts` (34 lines, 4 tests)
**Evidence:** Tests only check default port, custom port, host binding, and `isListening()` before start. No tests for:
- Starting and stopping the server
- Handling concurrent connections
- Error responses for invalid requests
- Graceful shutdown behavior

**Impact:** The HTTP transport is a network-facing component. The current tests verify only constructor defaults, not actual transport behavior.

**Recommended fix:** Add integration-level tests that start the transport, make HTTP requests, and verify MCP protocol responses. Test error paths: port already in use, connection refused, malformed requests.

#### M2: No shared test setup file — no `vitest.setup.ts`

**Evidence:** `vitest.config.ts` has no `setupFiles` configuration. There is no shared test helper module.

**Impact:** Every test file independently imports and configures its own helpers. Combined with H1 (makeEvent duplication), this means no single place to set up common test infrastructure.

**Recommended fix:** Create `tests/helpers/` directory with:
- `make-event.ts` — shared event factories (addresses H1)
- `make-frontend-error.ts` — shared FrontendError factory
- `setup.ts` — common vitest setup if needed

Several parser test files only test the happy path (`canParse` returns true, `parse` returns valid result) and a single "ignores unrelated lines" case. Missing:

**Recommended fix:** Add negative test cases for each parser: empty string input, null/undefined input (if applicable), malformed but similar-looking lines, extremely long input (>1000 chars per `MAX_RAW_LINE` constant).

#### M5: Performance benchmark thresholds are generous

**File:** `tests/perf/benchmark.test.ts`
**Evidence:** Thresholds are very loose:
- Parser registry: `expect(elapsed).toBeLessThan(1000)` for 10K lines (actual is likely <100ms)
- Secret redaction: `expect(elapsed).toBeLessThan(500)` for 10K lines
- Ring buffer: `expect(elapsed).toBeLessThan(100)` for 500 pushes
- Full pipeline: `expect(elapsed).toBeLessThan(2000)` for 1K lines

**Impact:** These thresholds would only catch catastrophic 10x+ regressions, not gradual performance degradation.

**Recommended fix:** Tighten thresholds to 2-3x the current actual performance. Add a baseline recording mechanism so regressions are caught earlier. Consider adding P95 latency checks for individual operations.

---

#### M6: Integration test gaps — no Docker Compose integration test

**Evidence:** `src/collectors/docker-log-collector.ts` has a unit test, but there is no integration test for the `tracepulse compose` command flow. The `multi-process-flow.test.ts` tests multi-process but not Docker-specific behavior.

**Recommended fix:** Add `tests/integration/docker-compose-flow.test.ts` (can be skipped in CI without Docker). Test service discovery from a compose file, container log tailing, and service name tagging.
