## 5. Findings

### HIGH Severity

#### H1: `makeEvent()` still duplicated across 24 files (was 23)

**Carried from TQR-001 H1. Worsened.**

The new `verify-fix-claim.test.ts` added a 24th copy. No shared helper was extracted. This is the single largest maintainability debt in the test suite.

**Estimated effort:** 2 hours to extract + update all 24 imports.

---

#### H2: 9 tool handlers have zero test coverage (was 8)

**Carried from TQR-001 H2. Worsened.**

`verify-build.ts` (3.8KB) was added without tests. The original 8 untested handlers remain untested. Combined, these 9 files represent ~27KB of untested MCP-facing code — the public API surface.

**Estimated effort:** 1 day for all 9 handlers (register-probe is the most complex).

---

#### H3: `verify-build.ts` — new composite tool with zero tests

**NEW finding.**

`verify-build.ts` orchestrates 3 steps (typecheck → build → runtime watch) with early-exit logic. It calls `handleRunAndWatch` and `watchForErrors` internally. Without tests:
- Early-exit on typecheck failure is unverified
- Build failure path is unverified
- Runtime error detection after successful build is unverified
- The `cwd` parameter passthrough is unverified

**Recommended fix:** Create `tests/unit/tools/verify-build.test.ts` with mocked `handleRunAndWatch` and `watchForErrors`. Test: all-pass, typecheck-fail-early-exit, build-fail-early-exit, runtime-errors-after-build.

---

#### H4: `empty-diagnostics.ts` — new utility with zero tests

**NEW finding.**

`empty-diagnostics.ts` maps tool names to diagnostic messages and routing hints. It's a pure function (`addEmptyDiagnostics`) that's easy to test. Without tests, diagnostic messages could silently break or return wrong routing hints.

**Recommended fix:** Create `tests/unit/tools/empty-diagnostics.test.ts`. Test: known tool returns diagnostics, unknown tool passes through, non-empty response passes through unchanged.

---

### MEDIUM Severity

#### M1: `error-lifecycle.ts` tested in wrong directory

**Carried from TQR-001 M1 (bundled tests). Still bundled.**

`src/store/error-lifecycle.ts` is tested inside `tests/unit/scoring/score-decay.test.ts`. The source lives in `store/` but the test lives in `scoring/`. This violates the 1:1 source-to-test mapping convention and makes the test hard to find.

**Recommended fix:** Extract to `tests/unit/store/error-lifecycle.test.ts`.

---

#### M2: `verify-fix-claim.test.ts` creates a second test file for `verify-fix.ts`

**NEW finding.**

`verify-fix.ts` is now tested in two places:
1. `tests/unit/tools/audit-missing-tests.test.ts` (basic PASS/FAIL)
2. `tests/unit/tools/verify-fix-claim.test.ts` (claim-checking)

Neither file is named `verify-fix.test.ts`. The tests should be consolidated into a single `tests/unit/tools/verify-fix.test.ts` covering both basic and claim-checking scenarios.

---

#### M3: Missing negative test cases in new parser tests

**Carried from TQR-001 M3. Partially addressed.**

The new `pydantic-parser.test.ts` has 2 negative cases but is missing:
- Empty string input
- Extremely long input (>1000 chars per `MAX_RAW_LINE`)
- Partial match: `"ValidationError"` without count
- Non-ASCII characters in model names

The `worker-parsers.test.ts` (celery, sidekiq, bullmq) still lacks:
- Empty string input for each parser
- Malformed task lines (e.g., missing brackets in BullMQ)
- Extremely long lines

---

#### M4: `audit-missing-tests.test.ts` bundles 5 tool handlers

**Carried from TQR-001 M1/L1. Still bundled.**

This file tests `get-health-summary`, `run-and-watch`, `verify-fix`, `wait-for-build`, and `wait-for-event` in a single file. The file name describes the meta-purpose rather than the source files.

**Recommended fix:** Split into 5 individual test files: `get-health-summary.test.ts`, `run-and-watch.test.ts`, `verify-fix.test.ts`, `wait-for-build.test.ts`, `wait-for-event.test.ts`.

---

#### M5: `error-narratives.test.ts` missing edge cases

**NEW finding.**

The test covers 10 of 10 narrative patterns plus the null case, which is thorough. However, it's missing:
- Pattern priority testing: when a message matches multiple patterns, does the most specific one win?
- Capture group edge cases: module names with special characters (`@scope/package`, `my-package.js`)
- Empty string input
- Very long error messages (>500 chars)

`applyScoreDecay` handles status codes 401, 403, 408, 429 (the `TRANSIENT_STATUS_CODES` set), but the test only verifies 401. The other three codes are untested.
