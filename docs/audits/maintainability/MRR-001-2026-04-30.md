# MRR-001 — Maintainability Review Report

**Date:** 2026-04-30
**Scope:** Full `src/` directory (65 source files)
**Reviewer:** Automated (Kiro)
**Codebase:** TracePulse v0.9.x — Node.js/TypeScript CLI + MCP server

---

## Executive Summary

TracePulse has a well-structured codebase with strong fundamentals: centralized constants, a clean parser interface, consistent type system, and thorough module-level documentation. The main structural concern is `src/mcp/server.ts` at 800+ lines acting as a monolithic registration hub. Tool handlers have a repeated response-wrapping pattern that should be extracted. Several inline magic numbers and one dead import need cleanup.

**Findings:** 14 total — 2 HIGH, 7 MEDIUM, 5 LOW

---

## Phase 1: Quick Wins

### F-01: Duplicate JSDoc block in `server.ts` for `handleGetErrors`

**Severity:** LOW | **Effort:** Quick Win
**File:** `src/mcp/server.ts` lines 81-95

There are two consecutive JSDoc blocks for `handleGetErrors`. The first (lines 81-90) describes the original contract. Then an `import` statement for `applyScoreDecay` appears at line 91 (mid-file, outside the import block), followed by a second JSDoc (lines 94-98) that supersedes the first.

```typescript
// Line 81: First JSDoc
/**
 * Handle get_errors tool - returns recent error/warn events sorted by signal_score descending.
 * ...
 */

/**
 * Handle get_errors tool - returns recent errors sorted by signal_score descending.
 * ...
 */
export function handleGetErrors(...) { ... }
```

**Fix:** Remove the first JSDoc block. Move the `applyScoreDecay` import to the top import block with the other imports.


Module-level mutable state violates the project convention that "All MCP tool handlers are pure functions that read from the event buffer — no side effects" (from `user-project-overrides.md`). This cooldown state should be injected or managed by the caller.

## Phase 2: Medium Effort

### F-07: Repeated response-wrapping boilerplate across 16 tool handlers

**Severity:** HIGH | **Effort:** Medium
**Files:** All 26 files in `src/tools/`

Every tool handler manually constructs `CallToolResult` objects with the same pattern:

```typescript
// Success pattern (repeated 38+ times across tools):
return {
  content: [{ type: "text", text: JSON.stringify(data) }],
};

// Error pattern (repeated 15+ times):
return {
  content: [{ type: "text", text: errorMessage }],
  isError: true,
};
```

`server.ts` already has `jsonResult()` and `errorResult()` helpers (lines 62-72), but they're private to that file. The tool handlers in `src/tools/` don't use them — they inline the same structure.

**Fix:** Extract `jsonResult` and `errorResult` into a shared module (e.g., `src/tools/response-helpers.ts` or `src/mcp/response-helpers.ts`) and import them in all tool handlers. This eliminates ~80 lines of boilerplate and ensures consistent response formatting.

```typescript
// src/mcp/response-helpers.ts
export function jsonResult(data: unknown): CallToolResult { ... }
export function errorResult(message: string): CallToolResult { ... }
```

### F-10: `handleGetErrors` and `handleGetServerLogs` live in `server.ts` instead of `src/tools/`

**Severity:** HIGH | **Effort:** Medium
**Files:** `src/mcp/server.ts` lines 81-170

The four Phase 1 tool handlers (`handleGetErrors`, `handleGetServerLogs`, `handleGetRuntimeStatus`, `handleClearErrors`) are defined directly in `server.ts` while all Phase 2-5 handlers are in separate files under `src/tools/`. This inconsistency:

1. Makes `server.ts` 800+ lines when it should be a pure registration file
2. Breaks the pattern established by every other tool handler
3. Makes the Phase 1 handlers harder to test in isolation

**Fix:** Extract each handler to its own file in `src/tools/`:
- `src/tools/get-errors.ts` → `handleGetErrors`
- `src/tools/get-server-logs.ts` → `handleGetServerLogs`
- `src/tools/get-runtime-status.ts` → `handleGetRuntimeStatus`
- `src/tools/clear-errors.ts` → `handleClearErrors`

This would reduce `server.ts` from ~800 lines to ~400 lines (pure registration + response helpers).

## Phase 3: Structural

### F-11: `server.ts` is a monolithic registration file (800+ lines)

**Severity:** HIGH (structural) | **Effort:** Large
**File:** `src/mcp/server.ts` — 800+ lines

`createMcpServer` registers 30 tools in a single function. Each registration block is 15-25 lines (schema + annotations + handler wiring). The function is ~600 lines long.

Beyond extracting the Phase 1 handlers (F-10), the registration itself could be decomposed:

**Fix (incremental):**
1. First, extract Phase 1 handlers (F-10) — reduces to ~600 lines
2. Group tool registrations into helper functions by phase:
   ```typescript
   function registerPhase1Tools(server, buffer, getConnected) { ... }
   function registerPhase2Tools(server, buffer, options) { ... }
   function registerPhase3Tools(server, options) { ... }
   // etc.
   ```
3. `createMcpServer` becomes a ~50-line orchestrator calling these helpers

This preserves the current architecture while making each phase independently readable and testable.

### F-12: Test parser pattern is consistent but could use a base helper

**Severity:** LOW | **Effort:** Large
**Files:** `src/parsers/test/*.ts` (6 files)

All 6 test parsers follow an identical structure:
1. Define regex patterns for FAIL/ERROR/SUMMARY
2. Implement `canParse` testing all patterns with `||`
3. Implement `parse` trying each pattern with `match()` in sequence
4. Return `ParsedError` with `framework: "<name>"` and `scoring_hints: { is_user_code: true }`

This is a clean, consistent pattern — not a problem per se. But if more test parsers are added, a `createTestParser(config)` factory could reduce boilerplate:

```typescript
const pytestParser = createTestParser({
  name: "pytest",
  patterns: [
    { regex: FAILED_PATTERN, level: "error", messageFrom: ... },
    { regex: SUMMARY_PATTERN, level: "warn", messageFrom: ... },
  ],
});
```

**Recommendation:** Not urgent. The current approach is readable and each parser is small (~60-80 lines). Consider this only if adding 3+ more test parsers.

## Positive Observations

These aspects of the codebase are well-executed and should be preserved:

1. **Constants centralization** — `src/constants/` with 7 domain-specific files and a barrel export is exemplary. Most constants are properly named and documented.

2. **Parser interface** — The `ErrorParser` interface (`canParse` + `parse`) is clean, and the registry's first-match-wins strategy with error isolation is robust.

3. **Type system** — `RuntimeEvent`, `ParsedError`, `EventBuffer`, `EventFilters` form a coherent type hierarchy. Type guards for MCP input validation are thorough.

4. **Module-level documentation** — Every file has a module-level JSDoc explaining purpose, architectural role, and cross-references. This exceeds the commenting standard requirements.

5. **Ring buffer design** — Fingerprint-based dedup, pinned high-signal errors, subscriber pattern, and bounded memory are well-implemented.

6. **Signal scoring** — Fully externalized to constants with clear calibration rationale. No magic numbers in the scorer itself.

7. **Secret redaction** — 16 named patterns with clear ordering rationale. Applied at the pipeline entry point before any storage.
