# MRR-004: Maintainability Review - 2026-05-17

| Field | Value |
|-------|-------|
| **Scope** | Full codebase (v0.9.19, 154 source files, ~16,600 LOC) |
| **Focus** | Response pattern consistency, file size, memory safety |
| **Findings** | 1 HIGH, 3 MEDIUM, 2 LOW |

## Executive Summary

TracePulse v0.9.19 is well-structured with clear separation of concerns. The main maintainability risks are:
1. Inconsistent MCP response construction (only 5/30 tool files use shared helpers)
2. Two oversized files (`server.ts` at 911 LOC, `cli.ts` at 797 LOC)
3. A memory leak in the rate limiter that affects long-running sessions

## Findings

### F-001: Inconsistent MCP response construction (HIGH)

**Category:** Pattern inconsistency
**Scope:** Systemic (25+ tool files)
**Evidence:** `src/mcp/response-helpers.ts` provides `jsonResult()` and `errorResult()` helpers, but only 5 of ~30 tool files use them. The remaining 25 construct responses inline with `{ content: [{ type: "text", text: JSON.stringify(...) }] }`.
**Why it matters:** When the MCP response format changes (e.g., adding metadata, changing content structure), 25 files need manual updates instead of 1. New tool authors copy-paste the inline pattern instead of using the helper.
**Recommended fix:** Migrate all tool files to use `jsonResult()`/`errorResult()`.
**Effort:** Low (mechanical find-replace)
**Regression risk:** Low

### F-002: `server.ts` at 911 LOC — too many responsibilities (MEDIUM)

**Category:** File size / decomposition
**Scope:** Local
**Evidence:** `src/mcp/server.ts` contains tool registration, 4 inline tool handlers (`handleGetErrors`, `handleGetServerLogs`, `handleGetRuntimeStatus`, `handleClearErrors`), and the MCP server factory.
**Why it matters:** The file is the hardest to navigate in the codebase. Adding a new tool requires scrolling past 900 lines. The 4 inline handlers break the pattern of every other tool living in `src/tools/`.
**Recommended fix:** Extract the 4 inline handlers to `src/tools/` files matching the existing pattern. The server.ts should only contain registration and wiring.
**Effort:** Medium (requires updating imports and tests)
**Regression risk:** Low

### F-003: Rate limiter unbounded memory growth (MEDIUM)

**Category:** Memory safety
**Scope:** Local
**Evidence:** `src/transport/rest-auth.ts` — the `windows` Map never evicts expired entries. Each unique client ID persists forever.
**Why it matters:** In long-running TracePulse sessions (common for dev servers), memory grows linearly with unique clients. Not critical for typical use (few clients), but violates the principle of bounded resource usage.
**Recommended fix:** Add a periodic cleanup that removes entries older than `windowMs`.
**Effort:** Low (10 lines)
**Regression risk:** Low

### F-004: `cli.ts` at 797 LOC — mixed concerns (MEDIUM)

**Category:** File size / decomposition
**Scope:** Local
**Evidence:** `src/cli.ts` contains argument parsing, pipeline creation, 3 collector factory functions (inline), and the main orchestration logic.
**Why it matters:** The file handles too many concerns. The inline collector factories duplicate logic that exists in the `collectors/` directory.
**Recommended fix:** Extract argument parsing to `src/cli/parse-args.ts` and pipeline creation to `src/cli/create-pipeline.ts`.
**Effort:** Medium
**Regression risk:** Low

### F-005: Inconsistent use of `as` type assertions for MCP args (LOW)

**Category:** Type safety
**Scope:** Systemic (all tool handlers)
**Evidence:** All tool handlers use `args.param as string | undefined` without runtime validation. While Zod validates at the SDK level, the pattern is fragile if the schema and handler drift.
**Why it matters:** Low risk today (Zod catches it), but if a schema is updated without updating the handler, the `as` cast silently produces wrong types at runtime.
**Recommended fix:** No immediate action needed. Document that Zod is the validation layer. Consider a typed args helper for new tools.
**Effort:** N/A
**Regression risk:** N/A

### F-006: Missing eviction in `perf-baseline.ts` path map (LOW)

**Category:** Memory safety
**Scope:** Local
**Evidence:** `src/store/perf-baseline.ts` stores per-path performance data in a Map with no size limit. A server with many unique API paths could grow this unboundedly.
**Why it matters:** Low risk for typical dev servers (few unique paths), but violates bounded-resource principles.
**Recommended fix:** Add a max-paths cap (e.g., 200) with LRU eviction.
**Effort:** Low
**Regression risk:** Low
